# 模式与风格库

模式决定证据出现的次序。风格决定投影时怎样读页面。例如同一组离线评测，在组会中用于讨论例外，在项目推进会上用于判断能否进入联调。两场报告可以使用同一种风格，但结尾要分别留下科学问题和项目决定。

## 六种汇报模式

| 模式 | 听众离开时应能回答 | 主线与收束 | 起稿 |
|---|---|---|---|
| 文献组会 | 文献的结论成立在哪些条件下？ | 问题与基线 → 方法和原图 → 主结果与分组 → 例外、局限和可检验的讨论题 | [journal-club](../assets/starters/journal-club.json) |
| 会议短讲 | 我能复述作者的哪项发现？ | 一个问题 → 一个核心想法 → 决定性证据 → 适用范围；长结果表移入备份 | [conference](../assets/starters/conference.json) |
| 研究与个人答辩 | 研究贡献如何得到验证？哪些由报告人完成？ | 交代研究主线 → 讲方法或公式 → 结果与对照 → 本人职责和未解决问题 | [defense](../assets/starters/defense.json) |
| 项目推进会 | 哪项工作改变了状态？谁需要作什么决定？ | 稳定的路线图 → 上期与本期 → 交付证据 → 依赖、负责人和下一检查点 | [progress](../assets/starters/progress.json) |
| 研制总结与验收 | 哪些指标能签署，哪些证据还缺？ | 范围与交付物 → 研制阶段 → 环境与基线 → 条款、测试编号、实测、记录和判定 → 遗留项 | [acceptance](../assets/starters/acceptance.json) |
| 项目路演与演示 | 谁用系统做什么？哪一步已实际跑通？ | 一次具体任务 → 使用路径 → 界面或现场证据 → 效果与下一次试用 | [demo](../assets/starters/demo.json) |

## 六种视觉风格

| 风格 ID | 识别特征 | 合适的页面和取舍 |
|---|---|---|
| evidence | 白底、墨绿结论标题与细分隔线 | 会议短讲、主结果。图与结论并置，表格只放关键比较 |
| editorial | 暖纸色、衬线标题、细横线和宽留白 | 文献组会、带原图的精读。长图裁到要解释的部分，讲解放在图旁 |
| seminar | 深色通栏标题、浅色正文、底部进度线 | 项目推进、学术讲堂。路线图与跨期状态表稳定沿用同一位置 |
| defense | 左侧章节导航、深色章页、浅色证据区 | 多章节答辩。章节名尽量短；高密度结果单独放入备份页 |
| review | 顶部深蓝细带、固定页脚、原生矩阵表 | 研制评审、验收。要求、编号、记录、判定按行对应 |
| stage | 深色画布、青色提示、较大的画面区 | 现场演示与项目路演。使用任务界面或现场照片，保证截图中的关键文字可读 |

风格和模式可交叉，例如 `starter acceptance 验收工作稿 --style defense`。替换风格后需要重看所选原图的背景、文字换行以及表格列宽。配色在 [styles.json](../assets/styles.json)，默认故事线在 [modes.json](../assets/modes.json)。

外部学术样稿、模板和各自影响见[设计来源](../UPSTREAM.md)。
